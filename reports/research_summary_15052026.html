1. Research question

The thesis claim, stated precisely
Can a multi-agent, retrieval-augmented system, working from medical literature, prioritise causal genes for rare-disease cases as well as a curated-database baseline — using phenotype information only?
Pinned by the question
  • Phenotype only. Input is HPO terms + a candidate gene list. No variant calls (VCFs), no allele frequencies, no zygosity.
  • Causal-gene prioritisation. Output is a ranked list over candidate genes; the metric of interest is whether the truly causal gene lands at the top.
  • Compared to a curated baseline. The reference is Exomiser HPO-only — the de-facto gold standard for phenotype-driven gene ranking.
What the claim is NOT
  • Not "agentic RAG beats an exome pipeline" — that would require variants.
  • Not "literature is better than curated databases for every gene-prioritisation task".
  • Not "LLM components always lift performance" — the Phase 2d ablations show this is conditional (and often null).
  • The narrower claim: for phenotype-driven gene-prioritisation, literature-RAG matches or beats curated-database approaches.

2. Why HPO-only mode and not full variant prioritisation

This is the single most important methodological choice; we record it here so a reviewer can locate the rationale.

Exomiser has two modes

ModeInputWhat it addsDatabase needs
HPO-only (Phenix, HiPHIVE) HPO terms + candidate gene list Curated gene–phenotype annotations from OMIM, Orphanet, MGI (mouse), ZFIN (zebrafish) ~5 GB phenotype data
Full variant prioritisation (PHIVE, ExomeWalker, hiPHIVE) HPO terms + VCF + pedigree Above + variant pathogenicity (CADD, REVEL), population frequencies (gnomAD), ClinVar ~50 GB

Why geno_agent uses HPO-only as the baseline

Inputs must match

Our pipeline takes HPO terms plus a candidate gene list. It does not take variants. Comparing it against Exomiser-full would be comparing an HPO-only system against an HPO+variant system — Exomiser-full would win by construction simply because it has more information. That comparison would not isolate what we are testing.

No data leakage

The Phenopackets we use contain a single declared causal variant per case. Feeding that variant in would leak the answer. The whole point of the test is: can we find the gene from phenotype alone?

Different research problem

Variant prioritisation is a different problem the thesis does not claim to solve. The narrower claim — that literature-RAG matches a curated-database approach on phenotype-driven gene ranking — is exactly what Cell K (Exomiser HPO-only) is the right anchor for.

Clinical-use framing

geno_agent's intended role is a literature-first triage step in workups where exome data is not yet available, or to augment exome workflows where variant scoring is inconclusive. Variants are downstream; phenotype-driven literature search is upstream.

Limitation worth flagging

The HPO-only baseline does not answer "is geno_agent better than a full clinical exome pipeline?" — and the thesis does not make that claim. Including a full variant pipeline would broaden the question beyond what our Phenopacket data supports (one declared variant per case, no exome VCFs available).

Authority for this choice: recorded in MASTER_PROJECT_v2.1.md §11.5 — "Cell E: Exomiser baseline — HPO-driven prioritization without literature evidence; the established gold standard for phenotype-driven gene ranking." (Cell E in the original spec; renamed Cell K in the extended factorial — see §10 deviation note.)

5. What we have learned so far

Finding 1 — Retrieval mode dominates

Hybrid (BM25+dense) vs dense-only: +49 pp top-1 under multi-agent (C→D), +12 pp under single-agent (A→B). Nothing else in the factorial moves the needle this much.

Finding 2 — Multi-agent pays off only under hybrid

Cell C (multi · dense) under-performs Cell B (single · hybrid) by 4 pp. The agentic architecture's value is conditional on retrieval being strong enough to surface useful chunks to grade.

Finding 3 — LLM augmentation has no main effect on top-1

Neither LLM-Planner nor LLM-Critic improves top-1 over the deterministic pipeline in either retrieval mode. Exception: LLM-Planner on dense (E vs C, +16 pp) — but only because it substitutes for the missing BM25 anchor.

Finding 4 — LLM Critic re-orders deeper ranks, not rank-1

The LLM Critic moves chunks at top-5 / top-10 (G top-5 +6.6 pp; H top-10 +1.4 pp) but does not change rank-1. Consistent with the retrieval-ceiling explanation: the deterministic Critic's heuristics already handle the unambiguous cases that dominate top-1.

Operational lesson

The first Cell G run had 71.6 % of LLM batches falling back to deterministic because prompts exceeded vLLM's 8 192-token budget. Fixed by reducing batch size 10→5 (commit 547b464). Silent fallback masked the bug for the duration of an entire overnight run — worth recording for future LLM-batching work.

7. Experiments planned

Cell K — Exomiser HPO-only (next, in parallel with I/J)

The critical missing comparison point. Without it, "Cell D = 0.627" is uninterpretable. Runs on CPU only — can start now in parallel with I/J on GPU.

  • Mode: HPO-only (Phenix + HiPHIVE)
  • Input: same 75 cases, same gene lists, seed=42
  • Setup: ~3–5 h (Java 17 + Exomiser CLI + ~5 GB phenotype data + wrapper)
  • Compute: ~5–15 s/case → ~20 min for 75 cases
Cells L – O — Cross-encoder re-ranker (Phase 2e)

Inserts a cross-encoder between retrieval and the Critic. The factorial isolates retrieval as the bottleneck; this is the literature-standard way to break it. Documented in master plan §11.8.

  • Default model: ncbi/MedCPT-Cross-Encoder (PubMed-fine-tuned, 440 MB)
  • Expected lift: +3 to +10 pp top-1 over Cell D
  • Setup: ~1 day; compute: ~5 h/cell · 4 cells
  • Stays inside master plan §11.1 — all local, no cloud LLM
